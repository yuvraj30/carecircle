# Plan for real WhatsApp reminders and background scheduling

**Status: design only.** CareCircle currently simulates reminder activity; the parent's phone in Sample is fictional, and reminders advance only while the app is open. No live provider, scheduler, migration, webhook, credentials or production deployment is included in this plan. Keep those limitations visible until the full flow is implemented and verified. Live reminders must not be relied on for medical or emergency care.

## Decisions required before implementation

- Choose the WhatsApp Business Platform provider and confirm its supported region, account verification, costs, quotas, data handling and testing environment. Provider choice is not implied by this document.
- Agree who operates the service, what support is available, what happens when a reminder fails, and how a caregiver can tell whether it was submitted, delivered or unanswered.
- Decide how a parent gives and withdraws permission to receive messages, and obtain any provider-required opt-in **before** sending an initial message. Do not treat creating a patient profile, a family member's consent, or a simulated reply as the parent's permission.
- Separately decide what the parent agrees to share, with which individual circle members, for which purposes. Permission to receive reminders is not permission to share message contents or use an external AI service.
- Review provider policy and privacy obligations with the responsible organisation. Decide retention, deletion, incident response, phone-number ownership verification, user support and a safe migration/backfill policy. Do not use real family data in development.

## Current system and proposed boundaries

The existing Supabase Edge Function in `supabase/functions/server/index.tsx` authenticates signed-in callers and checks active circle membership and role. Its circle modules and care events are kept as JSON values in `kv_store_e043d7e3`; the helper provides upsert and read operations, but not an atomic lease, compare-and-swap or a transactional message queue. The current reminder engine in `src/context.tsx` runs in a browser. These pieces should not be presented as a reliable background worker or used as the sole concurrency control for real sends.

Add the following as separate, testable components:

1. **Authorised care API:** retain the existing user-facing function's JWT and membership checks. Add explicit server-side role checks for every schedule, consent and care-event mutation. Do not trust a circle ID, role, schedule or patient identity supplied by a browser.
2. **Transactional Postgres store:** use migrations and private tables or carefully authorised functions for verified contacts, consent records, structured schedules, due occurrences, delivery attempts and inbound event IDs. Use database transactions and constraints rather than concurrent read/replace of KV arrays for messaging state. Design RLS and least-privilege service access; test that privileged service clients cannot be invoked by ordinary users.
3. **Separate inbound webhook function:** expose only the provider endpoint required to receive callbacks, independently of the user API. It must verify provider signatures before parsing or acting on any message and fail closed. If Supabase requires `verify_jwt = false` for this separate external webhook, do **not** disable JWT verification for the existing user function. Supabase describes the separation between platform JWT checks and provider-signature verification in its [Edge Function auth guidance](https://supabase.com/docs/guides/functions/auth).
4. **Private scheduling worker:** a scheduled job identifies due occurrences and invokes a separately authenticated service worker. The worker calls a provider adapter only when a feature flag and consent checks permit. Supabase Cron uses `pg_cron` and can invoke database functions or HTTP services; eligibility and deployment must be confirmed for the actual project. See [Supabase Cron](https://supabase.com/docs/guides/cron).
5. **Provider adapter:** a small interface that sends an approved template, normalises verified callbacks and classifies retryable/permanent errors. Keep provider-specific request signing, payload fields, window and template rules inside the adapter and test them against official provider documentation. Do not put provider secrets in browser code, Git, logs or example environment files.

## Inbound verification and identity

- Use HTTPS and validate the signature on the exact request bytes and/or original URL and parameters required by the chosen provider before any side effect. Use the provider's maintained verification library where available, validate required headers and rotate secrets. Handle provider verification challenges separately from signed message callbacks; a challenge token alone does not authenticate message content.
- For example, Twilio's validation uses the exact public URL and the provider's complete received parameters; JSON handling differs from form handling. Follow the [Twilio webhook security documentation](https://www.twilio.com/docs/usage/webhooks/webhooks-security) only if Twilio is chosen. Another provider's algorithm and handshake may differ.
- Link an incoming provider sender to a previously verified contact using a stable, unique mapping. A phone number alone can be reassigned or shared: define verification, change and re-verification flows, and quarantine ambiguous matches. Never accept an untrusted `circleId` or patient ID from incoming text as proof of access.
- Within one transaction, insert the provider event/message ID under a unique constraint and persist its processing state and resulting care-event changes. Duplicate deliveries must not create repeated care events; failures must leave the event eligible for safe retry rather than permanently marked processed. Verify signature and ownership before this processing, and acknowledge only after durable acceptance.
- Store the minimum needed message and audit data under explicit retention and sharing rules. Redact phone numbers and message bodies in application logs. Only expose parent reply text to members currently included in the parent's sharing agreement, and never automatically forward text to an AI provider without separate approved consent.
- Preserve exact received words where permitted, record interpretation as a proposal, and make uncertain, ambiguous, unknown or multilingual replies require human review. An incoming reply is not evidence that a dose was taken; only record the response or action that was actually received or confirmed. STOP/withdrawal must immediately prevent future dispatch, including queued items, subject to the selected provider's required acknowledgement rules.

## Consent and authorisation at send time

- Record a versioned, auditable, specific agreement with subject, channel, purpose, source, time and revocation state. Define distinct records for provider/channel opt-in, reminder agreement and sharing agreement; do not infer one from another.
- Before creating an occurrence and again immediately before each send, re-read current channel/reminder consent, contact verification, active patient and circle state, schedule version, quiet hours and operational kill switch. Suppress if withdrawn, unclear, expired, paused or if any required record is missing. Use transaction locks and version checks to serialize withdrawal with dispatch authorisation. A database transaction cannot recall a request already submitted to an external provider: define the cutoff, cancel queued work, surface in-flight/unknown outcomes and test the race explicitly.
- Only authorised circle coordinators/caregivers may request the operations permitted by their role. A service worker acts under narrowly scoped credentials, not a user's UI role or a public API key. Disclose when a message is queued, provider-accepted, delivered, failed or has unknown delivery; provider acceptance and delivery must never be labelled as parent acknowledgement.
- The first outbound message must comply with the selected provider's current opt-in and template rules, including any service-window restrictions. For example, Twilio describes approved templates for WhatsApp messages outside the customer-service window in its [template guidance](https://www.twilio.com/docs/whatsapp/tutorial/send-whatsapp-notification-messages-templates). Use approved, reviewed copy and minimise sensitive information visible on a locked screen.

## Scheduling, concurrency and failure handling

- Replace free-text frequency assumptions with a structured, clinician-supplied schedule and a required IANA timezone per schedule. A human must review and explicitly save a schedule; never infer or change a dose. Persist due instants in UTC and preserve the intended local date/time and timezone. Supabase recommends leaving the database timezone in UTC: [database timezone guidance](https://supabase.com/docs/guides/database/postgres/configuration).
- Define the product's behaviour for non-existent and repeated local times at daylight-saving transitions before enabling that timezone. Test both transitions, timezone changes, schedule edits, stopped medicines, quiet hours, clock skew and long outages. Do not silently skip, duplicate or shift a dose. Decide a conservative stale-occurrence policy with caregivers; never send a burst of old reminders after downtime.
- Use a deterministic occurrence key derived from a schedule version and intended occurrence, enforced by a database unique constraint. Claim due rows atomically with a lease and bounded batch; a lease expires after a worker crash. Create an outbox record in the same transaction as the intended care event.
- External delivery cannot be made exactly-once merely by locking a database row. If the provider offers idempotency or request lookup, use it and reconcile; otherwise a network timeout after submission has an **unknown** outcome. Do not blindly resend unknown submissions. Surface them for reconciliation/manual review under a documented retry policy to avoid duplicate or missed messages.
- Record state transitions separately: queued, claimed, submitted/accepted, delivered, failed, unknown and parent response. Webhook callbacks can be duplicate, delayed or out of order; deduplicate by provider ID and apply monotonic state transitions without overwriting a more authoritative outcome.
- Alert an operator about failed/unknown sends, expired leases, late jobs and webhook verification failures without exposing care text. Use bounded retries with jitter for known transient failures, a dead-letter/manual-review queue for exhaustion, and a global/circle/parent kill switch. Test disabled delivery as the default. Define a caregiver fallback rather than implying emergency monitoring.
- Store provider secrets in the platform secret manager and, where needed for database-driven jobs, restrict Vault access. Supabase notes that access to decrypted Vault secrets must be controlled: [Supabase Vault](https://supabase.com/docs/guides/database/vault). Protect job HTTP headers and logs as well. Keep a documented rotation and incident procedure.

## Verification plan

Use a fake provider, fake clock, fictional data and an isolated project for automated tests. No real parent should receive a message during development.

1. **Security:** valid, missing, invalid and tampered signatures; wrong account/sender; replayed callbacks; unauthenticated user API calls; role and circle isolation; secret leakage; provider challenge handling; webhook body-size and rate limits.
2. **Consent:** no opt-in, separate sharing refusal, withdrawal immediately before sending, repeated withdrawal, contact changes, expired consent and re-consent. Verify that simulated consent never enables the live adapter.
3. **Scheduling:** recurrence, local/UTC conversion, daylight-saving gaps and folds, quiet hours, medicine stopped, concurrent workers, lease expiry, duplicate jobs, same-time schedules, delayed job runs and no catch-up burst.
4. **Delivery:** accepted, delivered, permanent failure, transient failure, callback duplication/out-of-order, unknown timeout, provider outage, retry exhaustion, no automatic blind resend and correct user-visible states.
5. **Care and privacy:** separate parent reply sharing per member, unknown replies, unsafe text, role-limited access, signed-out access, audit consistency, retention/deletion and no protected content in logs or product telemetry. Confirm no dose or health outcome is inferred.
6. **End-to-end staging:** provider sandbox with authorised test identities, actual authentication and roles, approved templates, webhook reachability, server-driven execution while every browser is closed, user-visible status and manual recovery. Test rollback and disabling delivery. Document outcomes and known limitations.

## Deployment and rollout

1. Decide provider and operational ownership; complete review of consent, privacy, messaging copy and costs. Provision an isolated provider test account and staging Supabase project. Never paste credentials into chat, commits or shell output.
2. Build migrations and deploy the separately authenticated webhook/worker in staging. Configure provider callbacks, approved templates, restricted secrets and Cron only in the isolated project. Ensure cloned/restored projects do not run live jobs.
3. Pass automated tests and a documented staged end-to-end run. Confirm access controls and receive explicit approval for any real-recipient pilot. Feature flags remain off by default.
4. Before production, review migrations, backups, operational monitoring, alert ownership, rollback and recipient consent. Deploy the Edge Functions and scheduler separately from the frontend; merging frontend code alone does not deploy Supabase functions. Limit the pilot, monitor failures, and stop delivery if assumptions fail.

Until all of the above is implemented, tested and deliberately enabled, the app must continue to identify messaging and parent-phone activity as simulated.
